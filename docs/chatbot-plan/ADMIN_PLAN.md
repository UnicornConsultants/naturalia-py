# Naturalia 後台實作計劃

更新：2026-11-24。第一階段已實作；目前為本機測試帳本。使用方式及限制見 [後台說明](../../chatbot/ADMIN_README.md)。

## 已確認的方向

- 先建立自己可操作的管理後台，再把客人自助查詢與交易接到網站及 WhatsApp。
- Naturalia 充值是額外的獨立制度。充值帳戶、本金、贈額、有效期、扣款及退款以我們的資料庫為準，不使用 SHOPLINE store credits 作為帳本，也不自動把兩邊餘額加起來。
- SHOPLINE 是 B2C 店面，連接範圍只有第三方客服及導購插件。我們是獨立 B2B 業務系統；不將其會員、平台訂單或購物金當作 B2B 資料。
- 網站與 WhatsApp 共用後台及 Kimi K2.6；AI 可以整理需求或建立待確認草稿，不直接核款、調整餘額或批准退款。
- 現有 WhatsApp 管理頁可以沿用連線及人工接手功能。正式後台另加入登入、角色權限及操作紀錄，不能將目前僅限本機的管理頁直接公開。

## 第一階段交付

先做一個完整可測試閉環：員工登入 → 建客戶／帳戶 → 建充值方案 → 提交充值申請 → 財務核款 → 一次入帳 → 查明細／匯出對帳。

前端使用獨立管理介面，接現有 Python 應用；將目前 HTTP handler 拆出認證、充值、帳本及通道模組。本機測試沿用 SQLite，所有金額用整數分儲存，入帳以資料庫交易及唯一鍵保護。部署多人使用前再決定正式資料庫及執行環境。

先建立測試帳戶及清楚標記的測試方案，不自動匯入真實客戶餘額。舊 CSV 是樣本，不可當作真實帳本；若需要期初匯入，要先提供真實餘額表並核對、預覽、批准。

## 充值帳本設計

- **帳戶與聯絡人分開**：一個公司帳戶可有多位授權聯絡人；是否允許共用額度與哪些人可下單，須明確授權。不能按相同電話號碼自動合併帳戶。
- **每次充值分批記錄**：本金與贈額分開，保留當次方案版本及各自有效期；日後修改方案不改寫舊批次。
- **狀態**：充值申請 `待付款 → 待核款 → 已入帳`，另有 `拒絕／取消`。核准入帳與分錄同一資料庫交易完成。
- **只新增分錄**：充值、贈額、消費、退款、到期及更正各有來源單據。已入帳分錄不可直接覆寫或刪除；錯誤用有原因及批准人的沖正修正。
- **可用與預留分開**：可用額＝有效剩餘本金及贈額－有效預留額。取貨確認時原子檢查及預留，成功後扣款；失敗則取消預留。不能讓兩張訂單同時花掉同一餘額。
- **防止重複入帳**：同一充值申請／核准請求有唯一鍵；付款流水與渠道／交易編號作重複核對。按鈕連按、網絡重試不應再入帳。
- **核款**：付款截圖只作證據，需人工核對實際收款或可靠支付通知；AI 讀到截圖不能直接入帳。
- **退款分開**：退回充值額度和把現金付還客人是不同操作。需記錄退回哪個原批次、多少本金／贈額、有效期如何處理，以及是否有外部付款。

## 取貨及 SHOPLINE 關係

用戶已確認業務分離：B2B 取貨單與充值帳本由本系統管理，SHOPLINE 的接入僅限 B2C 客服及導購。先前「同步建立 SHOPLINE 訂單」選項不再作為本次實作方向。商品來源／連結可以來自公開店面，B2B 定價、規格、庫存及交付須按自己的業務規則處理。

## 角色與重要操作

| 角色（建議） | 可做 | 不可做 |
| --- | --- | --- |
| 客服 | 管理對話、建立充值／取貨申請、查看獲授權客戶資料 | 核准入帳、任意調整餘額 |
| 財務 | 核款、退款審批、對帳及匯出 | 無痕修改歷史分錄 |
| 管理員 | 管理員工、方案、權限、系統設定 | 刪除已入帳交易的稽核歷史 |

所有金錢操作記錄操作者、時間、來源單據、原因及金額。服務端驗證權限，不能只靠前端隱藏按鈕。是否要求申請人與批准人不同，或按金額門檻雙人批准，待營運安排確認。

## 主要資料表

`staff_users / roles`、`customers / account_contacts / external_identities`、`wallet_accounts`、`topup_plans / plan_versions`、`topup_requests / payment_evidence`、`credit_lots`、`ledger_transactions / ledger_entries`、`holds / allocations`、`fulfillment_orders / order_items`、`refund_requests`、`audit_events`；如要外部建單，再加 `integration_jobs`。

網站訪客 token、WhatsApp JID、SHOPLINE customer ID 都是外部身份索引；只有核實並授權綁定後，才可以讀取指定充值帳戶。對話記錄不等於錢包權限。

## 驗收要求

1. 同一核款請求提交兩次，只增加一次本金與贈額。
2. 兩個職員同時扣款不能造成負數餘額；失敗的取貨單會釋放預留。
3. 客服角色不能直接呼叫核款／退款批准 API。
4. 每次餘額變動可追溯到原單據、方案版本、操作者及原因。
5. 修改新方案不改變已充值批次；到期及退款按確定的批次規則測試。
6. 未綁定或其他客戶的網站／WhatsApp 身份不能讀取帳戶餘額。
7. 對帳匯出與帳本一致；CSV 內容處理公式注入，匯出按權限限制。
8. 獨立充值流程不呼叫 SHOPLINE store credits 增減接口。

## 待確定的業務規則

- B2B 內部取貨單的定價、規格、庫存及履約流程。
- 手續費 2.3%／2.5% 的適用方案，以及手續費是否轉成額度。
- 自有充值方案的有效期；網站 SHOPLINE 購物金 180 日不能套用。PDF 一年亦需確認為現行規則。
- 本金／贈額哪個先扣；是否按最早到期批次扣款。
- 贈額是否可退、部分退款比例、退款額度是否沿用到期日。
- 公司共用帳戶、授權聯絡人及核款人員安排。

以上尚未確認的欄位先做成可配置及測試用設定，不擅自啟用真實交易。
